SOLID Principles:

1. Single Responsibility Principle
2. Open/Closed Principle
3. Liskov's Substitution Principle
4. Interface Segregation Principle
5. Dependency Inversion Principle

------------------------------------------------------------------------------------------------------------------------------------------------------------------

Single Responsibilty Principle:

    - A class should have only one reason to change.
    - A class should have only single purpose or Responsibilty.

    - Bad Example: 

        class UserService {
                public void saveUser(User user) {
                    // Save user to DB
                }

                public void sendEmail(User user) {
                    // Send welcome email
                }

                public void generateReport() {
                    // Generate report
                }
        }

    This class has 3 responsibilities:
        - User management
        - Email sending
        - Report generation

    Good Example:

        class UserService {
                public void saveUser(User user) {
                    // Save user
                }
            }

            class EmailService {
                public void sendEmail(User user) {
                    // Send email
                }
            }

            class ReportService {
                public void generateReport() {
                    // Generate report
                }
            }

Open/Closed Principle:

    - A Class should be open for extension but closed for modification.
    - You should be able to add new functionality without modifying existing code.
    - We achieve this commonly through interfaces, abstract classes, polymorphism, and composition.
    
    Bad Example: 

        class PaymentService {

            void pay(String paymentType) {

                if (paymentType.equals("CREDIT_CARD")) {
                    System.out.println("Processing credit card payment");
                }
                else if (paymentType.equals("PAYPAL")) {
                    System.out.println("Processing PayPal payment");
                }
            }
        }

    - Adding a new payment type means modifying existing code.

    Good Example:

        // Create an Interface 

        interface Payment {
            void pay();
        }

        // Then create implementations

        class CreditCardPayment implements Payment {

            @Override
            public void pay() {
                System.out.println("Processing credit card payment");
            }
        }

        class PayPalPayment implements Payment {

            @Override
            public void pay() {
                System.out.println("Processing PayPal payment");
            }
        }

        class UPIPayment implements Payment {

            @Override
            public void pay() {
                System.out.println("Processing UPI payment");
            }
        }

        // Now the service doesn't care about specific payment type    

        class PaymentService {

            void processPayment(Payment payment) {
                payment.pay();
            }
        }


        Real World Example: 

        Notification
            ↑
        ┌───┼────┬──────┐
        Email SMS  Push   WhatsApp

        - If your application already supports Email and SMS, adding WhatsApp should ideally mean adding a new WhatsAppNotification implementation, 
        rather than modifying a large NotificationService with another if/else.

Liskov's Substitution Principle:

    - This principle “Derived or child classes must be substitutable for their base or parent classes“. 
    - Any class that is the child of a parent class should be usable in place of its parent without any unexpected behavior.
    
    Bad Example: 

        class Bird {
            void fly() {}
        }

        class Sparrow extends Bird {

            @Override
            void fly() {
                System.out.println("Sparrow is flying");
            }
        }

        class Penguin extends Bird {

            void fly() {
                throw new UnsupportedOperationException();
            }
        }

        // Now consider 

        void makeBirdFly(Bird bird) {
            bird.fly();
        }

        makeBirdFly(new Sparrow());  // Works ✅
        makeBirdFly(new Penguin());  // Exception ❌

        // Penguin is a bird that canot fly. This breaks expectations as it cannot be used as substitute for Bird class (Parent class)

    Good Example:

        class Bird {}

        interface Flyable {
            void fly();
        }

        class Sparrow extends Bird implements Flyable {
            public void fly() {}
        }

        class Penguin extends Bird {}

        void makeBirdFly(Bird bird) {
            bird.fly();
        }

        makeBirdFly(new Sparrow());  // Works ✅
        makeBirdFly(new Penguin()); // will not compile

        // This is better because the type system itself prevents invalid behavior.

Interface Segregation Principle:

    - Do not force any client to implement methods of an interface which is irrelevant to them
    - Instead of creating one large interface, create smaller, focused interfaces.

    Bad Example:

        interface Worker {
            void work();
            void eat();
            void sleep();
        }
        
        // Robot Workers do not eat or sleep

        class Robot implements Worker {
            public void work() {}

            public void eat() {
                throw new UnsupportedOperationException();
            }
        }

    Good Example:

        interface Workable {
            void work();
        }

        interface Eatable {
            void eat();
        }

        interface Sleepable{
            void sleep()
        }

        class Human implements Workable, Eatable, Sleepable {}

        class Robot implements Workable {}

    Another Example:

        interface Printer {
            void print();
            void scan();
            void fax();
        }    

        class BasicPrinter implements Printer{

            public void print(){
                System.out.println("Printing..")
            }

            public void scan() {
                // Not supported
            }

            public void fax(){
                // Not supported
            }

        }    

        // Here the class is forced to implement the scan & fax methods

        Better Design: 

        interface Printable{
            void print()
        }
        
        interface Scanable{
            void scan()
        }

        interface Faxable{
            void fax()
        }

        class BasicPrinter implements Printable{
            
            public void print(){
                System.out.println("Printing..")
            }
        }

Dependency Inversion Principle:

    -  High-level modules should not depend on low-level modules. Both should depend on abstractions. 
    -  Abstractions should not depend on details. Details should depend on abstractions.

    - Bad Example

        // Let us consider that we have a OrderService that sends email
    
        class EmailService {
            void sendEmail(String message) {
                System.out.println("Sending Email: " + message);
            }
        }

        // Order Service directly depends on EmailService

        class OrderService {

            private EmailService emailService;

            OrderService() {
                emailService = new EmailService();
            }

            void placeOrder() {
                System.out.println("Order placed");

                emailService.sendEmail("Your order has been placed");
            }
        }

        // If tomorrow we want to send an SMS instead of Email we have to modify the Order Service.
        // As the order service is tightly coupled to the concrete Implementation.

    - Good Example 

        // Instead of making OrderService depend directly on EmailService, create an abstraction.

        interface NotificationService {
            void sendNotification(String message);
        }

        // Now Email Service implements abstraction

        class EmailService implements NotificationService {

            @Override
            public void send(String message) {
                System.out.println("Sending Email: " + message);
            }
        }

        class SMSService implements NotificationService {

            @Override
            public void send(String message) {
                System.out.println("Sending SMS: " + message);
            }
        }

        // Now OrderService depends on the interface, not the concrete class

        class OrderService {

            private NotificationService notificationService;

            OrderService(NotificationService notificationService){
                this.notificationService = notificationService 
            }

            public placeOrder(){

                // Place order logic implementation

                notificationService.send("Your order has been placed");

            }
        }

        // Now we can inject whichever implementation we want

        EmailService email = new EmailService();
        OrderService orderService = new OrderService(email);

        SMSService sms = new SMSServcie();
        OrderService orderService = new OrderService(sms); 

-----------------------------------------------------------------------------------------------------------------------------------------

SRP → One component/hook = one job.
OCP → Add new features via extension, not by editing existing logic.
LSP → Any derived component/service should behave as expected when used in place of its base type.
ISP → Small, focused prop interfaces and APIs.
DIP → Inject services and API clients rather than hard-coding them.
